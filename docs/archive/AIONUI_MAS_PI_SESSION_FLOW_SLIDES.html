整体链路

这不是 AionUI 直连大模型，而是经过 MAS 编排

AionUI用户界面、输入输出、审批弹窗，是 ACP Client。
ACP stdioJSON-RPC 通道，负责协议消息传输。
MAS自定义 ACP Agent，负责会话、编排、安全边界。
Pi SDK实际 coding agent 内核，负责工具调用与模型交互。
大模型生成推理、计划、代码和工具调用意图。
MAS 是中间的“会话与治理层”：它把 UI 会话、内部角色、工具权限和 Pi 执行串成一个可审计流程。
AionUI → ACP → MAS → Pi → Model2 / 9
组件职责

各层只做自己该做的事

AionUI

负责展示对话、接收用户输入、展示 MAS 回传的更新，并在需要时弹出权限审批。

ACP 层

负责握手、创建 session、接收 prompt、发送 session/update 与 request_permission。

MAS Core

负责 HA / Ego / Superego 编排、上下文构造、验收、返工和审计记录。

Pi Adapter

负责创建 Pi session、映射 Pi 事件、拦截工具权限、把执行结果回传给 MAS。

Pi SDK

负责 coding agent 执行，包括模型调用、工具选择、读写文件和命令执行。

大模型

负责语言推理、任务分解、代码生成、工具调用意图和结构化输出。

职责边界越清楚，会话一致性越容易维护3 / 9
一次对话阶段

从用户输入到最终回复的 8 个阶段

启动 AgentAionUI 启动 mas acp，通过 stdio 建立 ACP 通道。
协议握手MAS 返回 agent 能力、模式、配置项等元信息。
创建会话ACP 层创建或加载 sessionId，并同步给 AionUI。
接收 promptAionUI 带着 sessionId 调用 session/prompt。
HA 路由HA 判断是直接回答、澄清，还是交给 Ego 执行。
Ego 执行Ego 通过 Pi SDK 与模型和工具交互，产出执行结果。
Superego 验收基于执行结果和审计证据判断通过、返工或升级人工。
HA 汇报MAS 把最终结果作为 ACP 更新返回 AionUI。
每次用户输入是一条 run，但仍属于同一个 session4 / 9
核心问题

谁负责把 AionUI 会话和 Pi 会话对齐？

答案：MAS 负责

准确地说，ACP Server 是会话身份源头，Core Runner 负责贯穿，Pi Adapter 负责把这个身份标记到 Pi 事件和权限请求上。

不是谁负责

  • AionUI 不理解 MAS 内部 HA / Ego / Superego 编排。
  • Pi 不拥有 AionUI 会话身份的最终解释权。
  • 大模型只看到被 MAS 构造后的任务上下文。
同一个会话的标准身份是 MAS 的 sessionId，所有上下文、事件、审批和最终回复都围绕它归档。
会话一致性由 MAS 兜底5 / 9
身份模型

sessionId、runId 和 Pi session 是三种不同身份

会话级

sessionId

表示 AionUI / MAS 里的同一个对话。用于恢复历史、压缩摘要、发送 session/update、记录 messages 和 events。

任务级

runId

表示这个会话中的一次执行。用户每发起一次任务，MAS 会创建新的 run，用于审计和状态追踪。

执行级

Pi session

表示某个 HA、Ego 或 Superego 角色的一次 Pi agent 执行实例。当前主要是临时执行载体。

关键关系：一个 sessionId 可以包含多个 runId；一个 runId 内可能创建多个 Pi session，例如 HA 决策、Ego 执行、Superego 评审。
不要把 UI 会话、任务执行和 Pi 实例混成同一个概念6 / 9
对齐机制

MAS 用同一个 sessionId 贯穿链路

位置 做什么 对齐作用
src/acp/server.ts session/new 创建 mas-${uuid}，session/load 恢复指定会话。 建立 AionUI 与 MAS 共同认可的会话 ID。
src/storage.ts 按 session_id 存储 messages、context、runs、events。 让后续 prompt 能恢复同一会话历史。
src/core/runner.ts run(prompt, options, sink, sessionId) 创建新 runId，但保留原 sessionId。 把同一会话内的多次任务执行串起来。
src/pi/pi-sdk.ts createPiSession({ sessionId, runId, role }) 把身份带入 Pi 事件和审批。 让 Pi 侧事件回到正确的 AionUI/MAS 会话。
对齐不是靠 Pi 自己记住 UI 会话，而是靠 MAS 传递和归档身份7 / 9
审批与事件回传

工具调用也必须回到同一个会话

权限请求

Pi 触发写文件、编辑文件或命令执行时，MAS Pi Adapter 拦截工具调用，并通过 ACP session/request_permission 发给 AionUI。

事件回传

Pi 的 message、tool_call、tool_result 等事件会被 MAS 记录为带 sessionId、runId、role 的审计事件。

Pi 工具意图模型决定调用工具。
MAS 拦截判断读写与命令权限。
AionUI 审批展示请求并等待用户决定。
继续执行批准后放行，拒绝则反馈失败。
审计归档记录到同一个 session/run。
审批链路也使用同一个 sessionId8 / 9
结论

当前架构的重点与边界

已经明确的责任

  • AionUI 管界面和审批。
  • ACP 层管协议和 UI 会话。
  • MAS Core 管编排、上下文和验收。
  • Pi Adapter 管 Pi 事件映射和权限拦截。
  • Pi SDK 和大模型管具体执行与生成。

当前实现边界

  • Pi session 当前更像执行实例，不是 AionUI 会话的长期主记录。
  • 跨轮上下文主要由 MAS storage 的摘要和最近消息恢复。
  • 会话一致性要继续依赖 sessionId 的贯穿、审计和回放。
一句话：AionUI 负责“看见会话”，Pi 负责“执行任务”，MAS 负责定义并维护“这是不是同一个会话”。
