先给结论

“同一个会话”的责任方是 MAS

AionUI 看见会话

AionUI 负责展示对话、接收用户输入、带回 sessionId，并展示权限审批。

MAS 定义会话

MAS 用 sessionId 归档消息、摘要、事件、审批和任务执行记录。

Pi 执行任务

Pi session 当前是角色级执行实例，不是 AionUI 会话的长期主记录。

当前会话连续性来自 MAS 的 SQLite 上下文恢复，而不是 Pi 的持久会话恢复。
关键区分：UI 会话、MAS run、Pi session2 / 10
身份模型

sessionId、runId、Pi session 不是一回事

身份含义生命周期
sessionId AionUI / MAS 共同识别的用户对话身份。 跨多次用户请求存在，用于恢复上下文和回放事件。
runId 同一会话中一次用户请求对应的一次 MAS 执行。 每次 session/prompt 通常创建一个新的 run。
Pi session HA、Ego 或 Superego 某一轮调用 Pi SDK 创建的 agent 实例。 当前主要是内存型执行实例，用完释放或结束。
一个 sessionId 可以包含多个 runId；一个 runId 内可能创建 HA、Ego、Superego 多个 Pi session。
身份边界清楚，才能解释为什么要由 MAS 做对齐3 / 10
请求阶段

一次用户输入经历这些步骤

创建或加载会话AionUI 调用 session/new 或 session/load。
MAS 记录活动会话MAS 把 sessionId 写入进程内 sessions map。
AionUI 带回身份用户输入后，AionUI 用同一个 sessionId 调用 session/prompt。
MAS 查活动状态MAS 用 sessions.get(sessionId) 找 cwd、模式和技能。
MAS 恢复上下文MAS 从 SQLite 取摘要和最近消息。
构造本轮任务MAS 把历史、技能摘要和当前请求拼成 prompt。
Pi 执行角色任务HA、Ego、Superego 需要时分别创建 Pi session。
结果回写会话MAS 保存助手回复和事件，再通过 ACP 更新 AionUI。
每次请求都重新经过 MAS 的上下文构造4 / 10

持久化

MAS 用 SQLite 保存会话记忆和审计证据

表作用会话关系
messages保存用户和助手消息。通过 session_id 归属到同一 AionUI 会话。
session_context保存压缩摘要和已摘要消息位置。用 session_id 恢复早期上下文。
runs保存每次任务执行状态。一个会话下可以有多条 run。
events保存 MAS / Pi 事件流。同时带 run_id 和 session_id。
approvals保存工具审批结果。通过 run 和事件链路回到会话。
SQLite 是 MAS 的会话记忆来源，也是审计和回放的事实来源。
对应文件：src/storage.ts6 / 10
上下文构造

MAS 不是让 Pi 自己找历史，而是显式注入上下文

const task = buildTaskWithConversation( prompt, options.conversationHistory, options.conversationSummary, options.availableSkills, ); // 任务中会包含： // - 同一 AionUI 会话的历史说明 // - 已压缩的早期上下文摘要 // - 最近历史对话 // - 当前用户请求

好处

MAS 能明确控制哪些历史进入本轮任务，并能结合技能、审批和验收策略。

代价

上下文需要 MAS 每轮重新拼接，长会话时需要摘要和裁剪策略。

对应文件：src/core/runner.ts7 / 10
Pi 执行实例

当前 Pi session 是内存型角色执行实例

const { session } = await pi.createAgentSession({ cwd: options.cwd, tools: roleTools, customTools, sessionManager: pi.SessionManager.inMemory(options.cwd), resourceLoader, });

HA

只做路由、澄清、直接回答判断，默认不开放写入能力。

Ego

负责真实执行，可以读写文件、编辑文件和运行命令，但受审批约束。

Superego

负责评审和验收，当前以只读工具为主。

当前代码没有保存 Pi 持久 session id，也没有在下一轮用 Pi session id 恢复历史。

设计取舍

为什么不直接复用 Pi 会话 ID？

问题当前选择原因
会话语义以 MAS sessionId 为准AionUI 会话可能包含多个角色和多次执行。
角色隔离HA / Ego / Superego 分别创建执行实例不同角色的工具、权限、prompt 和职责不同。
上下文治理MAS 负责摘要、裁剪和注入需要配合审批、审计、验收和返工。
审计追踪事件统一归档到 MAS SQLite便于按 sessionId 和 runId 回放。
这不是不能复用 Pi 会话，而是 MVP 阶段先把治理权放在 MAS9 / 10
未来演进

如果要复用 Pi 会话，需要新增显式映射层

MAS sessionId用户对话主身份
HA Pi ID路由角色历史
Ego Pi ID执行角色历史
Superego Pi ID评审角色历史
对账策略MAS 与 Pi 历史一致性

需要补的设计

Pi session id 持久化、角色隔离、摘要冲突、事件对账、SDK 升级兼容。

当前推荐

MVP 继续由 MAS 存上下文、恢复历史、注入任务，把 Pi 作为角色级执行内核。

一句话：AionUI 负责看见会话，MAS 负责维护会话，Pi 负责执行任务，大模型负责生成结果。
